# 业务规则登记与活体改动

用于长期运行、由数据库、电子表格和作业说明共同支撑的业务系统：同一条规则被反复重新决定，旧文档互相矛盾。
也用于：要登记一次规则决定、要改活体表格或成本模型、要把作业单交给另一个执行者、以及在规则改动落到活体件
之前的那一刻。

## 工作流

1. **规则不进登记表，就等于没发生。**

   | 载体 | 承载 | 绝不承载 |
   |---|---|---|
   | 工作日志（按天） | 做了什么、还开着什么、下次起点、控制数 | 当前规则（它会漂移） |
   | 经验文档 | 一条可复用的经验：原因、纠正、如何避免 | 过程性议论 |
   | 规则登记表 | 当前规则的唯一权威清单；被取代的条目保留并标注 | 推理与死胡同 |
   | 作业单 | 给一个执行者的可执行说明，引用登记表条目编号 | 在单子里新造的规则 |

2. **只建一个登记表文件**，条目按域编号（`<PREFIX><n>`）：治理、产品、合同、物流、资金、成本。前缀不得
   与实体名混淆——表叫 `F04` 时规则编号 `F4` 会被误读——用域词前缀（`FD`、`CT`、`LG`）或 `R-<domain>-<n>`。
3. **每条写成 `id | rule | status | landed | source`。** 不设 `date` 列，也不设 `decided by` 列：登记表记的
   是确认了什么，不是谁在何时说的，逐行写人名会把它变成日志。日期放单独的来源附录，正文里也不写。
   - 措辞只写已确认的做法：不写决策人原话、不写口述、不写拍板、不写建议。未确认的规则在确认前不进登记表。
   - `source` 必须能定位到东西：`ledger YYYY-MM-DD / <条目 id>`，或同目录相对链接。"9/17 业务组"、
     "10-11 会话"一年后什么都定位不到；可靠的做法是当天写一行台账，绝不事后重建。这条线索放附录，
     附录里写建立、校验和链接的做法；正文条目集合必须与附录条目集合相等。`source` 指向登记表自身，
     或只写版本号（`v1.1 新增`），定位到的是"何时"而不是"为何"：这类行要清零。
   - `status`：effective（生效）/ superseded（被取代）/ pending（待定）。不要就地改写条目——新增一条，
     把旧的标成 `superseded → <新 id>`，让演进过程看得见。被否决的提议保留为 `status: closed` 并写明理由。
     每条待定决定都要记下"未定之前按什么默认值执行"。
   - `landed`：built / partial / not built / needs read-back，靠读活体系统填，不靠计划填，
     这样已决定的规则不会被误当成已实施的。
4. **让过期文字看起来就是过期。** 每份新工作日志开头写一段简短的"当前有效"摘要；长文档里被取代的章节
   就地标注（`本节已被 <id> 取代`）。回读审计落成一个有日期的章节，声明它覆盖所有条目的 `landed` 列，
   而不是逐格改几十个单元格。
5. **作业单只引用规则，不定义规则。** 抬头写：它依赖的登记表条目编号、执行者、前置条件、有效期、
   撤销条件（哪条规则一变就作废）。被引用的规则一变，签发方撤销并重发；执行者遇到冲突要停下来上报，
   不许即兴改出一个碰巧能跑通的变体。交付要求也要写进单子：每次改完读回、报出验收控制数、报错原文照贴、
   列出用了哪些退路。
6. **先把输入核实，再落地。** 规则改动常常靠一个二手数字——口头报来的装载数、老表格里的一个单元格——
   先拿主数据做自洽检验：单件体积 × 每柜件数 对 柜容量（应在几个百分点内一致）；各分摊份额合计 100%，
   分摊分母等于 Σ(数量 ÷ 单位容量)。如果系数只是因为那个可疑数字才凑得上，这个漂亮结果本身就是线索。
   不合格就不落地、也不做"平均"：把两边数字连同等式的矛盾一起报出，要求给书面来源，因为一个没核实的
   乘数会无声地污染下游每个价格。
   - 不合格的值常常不是错误而是估算——供应商投产前的猜测，从未被真实运行校验过。按"物理上不可能 ⇒
     两个字段里至少一个没核实"报出，由业务方定性；持久的修法通常是一条规则（成本与报价只许用实测输入），
     而不是改那个数字。
   - 两个输入可能落在不同的装满基准上（一个按件数封顶、一个按体积封顶），所以按 Σ(数量 ÷ 单位容量) 算出
     的分摊分母合法地超过实际柜数。两种修法都自洽：保留偏大的分母并在模型自己的说明里写明，或按柜归一
     （分母 = 实际柜数，混装柜内每行乘 1 ÷ Σ(该柜内柜位)）。选定一种并用到每个费用池——两种机制各自
     合计 100%，但同一笔费用分摊到各型号会差几个百分点，于是按一种机制做的表与按另一种机制做的登记表份额
     互相矛盾，而任何一份文档都解释不了。存在混装柜时，按柜归一更贴近业务方的思考方式（"批次费用除以柜数，
     再按柜位分柜内内容"），也和柜级费用一致；优先用它，偏大的 Σ 只留作校验单元格。改完再验一遍：
     数量 × 单位分摊仍应加总到总额。
   - 要定位"份额对不上"，就按每个候选机制算出各型号应有份额，与登记表里的份额对比：这样立刻指认哪一侧
     过期，而不必把整个模型重算。
   - 让分母单元格的标签与它的含义一致。自动求和的柜位合计和手工填的实际柜数不是一个数；标签写"柜位合计"
     而提示写"柜数"，是业务方问"这格该填什么"最常见的原因。
7. **一次只改一类。** 先备份（拷进归档目录，加 `_pre-edit` 后缀）并报出备份路径。每改完一类，用控制数校验，
   并对每个变动的值逐行报改前/改后。取代，不覆盖：旧条目标 `superseded → <id>`，新条目写明推翻它的证据。
   当指令与已登记的规则冲突时，带证据把矛盾摆出来，按业务方的决定执行，并把结果登记——推翻自己先前的改动
   很正常，就直接说清并给出算式，别悄悄改数。
   - 往 markdown 登记表里插入条目：锚定整行原文。只替换行首片段会把旧行尾巴粘到新文字后面，两个条目并成
     一行；每次插入式编辑后读回 diff，若并行了，就在那段唯一的粘连文字上再补一次拆分。
   - 表结构调整（删/加一列、章节重编号）是脚本活：放宽条目 id 正则，别让被取代的变体（`CT3-old`、
     `CT10R`）落空而保留旧列数；同一遍里重编号每一处 `§N` 交叉引用，且从大到小（先 `§10→§11`
     再 `§9→§10`）；再证明正文没被破坏：把新附录剥掉，与改前备份 diff，唯一允许的差异是你加的分隔线。
8. **把重新决定的规则扫过每一个载体。** 规则文字是这件活里最小的部分——同一条规则会被复制到登记表条目、
   角色手册、规格书、导航页、检查清单表、本地知识文件、试运行表和 agent 技能里。动手前先按活体目录树
   列出载体：登记表条目（权威副本与云端副本）、各角色手册、规格文档、入口或导航页、说明"东西放哪"的指引文档、
   检查清单表、本地知识索引、试运行计划与执行者说明、执行该规则的技能、云端页面的本地镜像、日志与台账行。然后：
   - 留取代痕迹，绝不删除：旧条目保留原文并把 `status` 标成 `superseded → <新 id>`，新条目写明推翻了什么，
     登记表的变更附录加一行。其他文档里的历史变更行保留旧措辞——那是历史，不是指令。
   - 扫表格的列，不只扫正文。跨越边界的检查行必须在每个承载归属的列上一起移动：谁提供、谁跟进、是否必需、
     触发时点、阶段名——阶段值是一个选项值，改名要按与其他受控改名相同的纪律做。
   - 用"逐载体数被取代词"来验收，不靠重读文档：扫完后剩下的每处命中都必须是被取代说明或历史行，
     其他任何命中都是漏项。
   - 把规则写在人和别的 agent 都会读到的地方：登记表与共享页面是源头，自己的技能只是引用它们的执行辅助，
     规则只活在技能里就会被下一个人或下一个 bot 重新发明。
   - 宁可"写清的规则＋按需检查"，不要定时巡检：周期性轮询不是保持正确的方式，而任何人都能在需要时跑的
     只读检查器，作为可双击的手动工具是受欢迎的，作为定时器不是。
   - 就地编辑不会留下可见痕迹，所以报"节点 → 章节"的路径并让对方刷新页面；只说"改好了"等于"什么都没发生"。
9. **改活体电子表格模型而不弄坏它。**
   - 只写单元格值，让已有公式、数字格式和合并单元格活下来；写空单元格时从相邻单元格抄样式。保存前打开
     工作簿的"完全重算"标记：编辑器本身不算，保存又会丢掉缓存结果，不打开这个标记，文件在别人重开之前是空的。
     然后无头重算（`soffice --headless --norestore -env:UserInstallation=file:///<临时配置>
     --convert-to xlsx --outdir <临时目录> <文件>`），以带缓存值的方式读转换后的副本，再核控制数。
     解释器缺 `openpyxl` 就建个一次性环境（`uv venv -p <明确的 python 路径> <临时目录>`——不给 `-p` 时
     `uv` 会抓它最先找到的解释器——再 `uv pip install --python <临时目录>/Scripts/python.exe openpyxl
     pillow pypdfium2`）。用脚本去调表格二进制的辅助程序，可能在非 UTF-8 控制台上解码本地化输出时挂掉；
     这时直接调二进制，别重试辅助程序。
   - 同一值出现在多张表里，就必须是一个权威字段加查找。审计时把副本 diff 出来报漂移——手打的重复值会悄悄
     分叉。改了某个小计列的含以后，所有消费它的列都要重新推导：已经自己加过各项的合计会再加一遍，
     所以要逐行核对最终列 = 小计 + 只属于小计不再负责的项。
   - 给模型两列成本："已知成本"把尚未填的费用池当 0，这样在对方还没给数时就能先报价；"最终成本"在输入不全
     时留空——只用一列，要么藏住部分结果，要么把部分结果打扮成完整的。共用同一个输入的章节互相引用（`=B21`），
     让一个数字只在一处维护，并说明这一点：局部覆盖就是直接在公式上填数。
   - 报之前把备份与改后文件逐格 diff（值和公式都比）：它产出给第三方的变更清单，也是同时抓出自己误改和
     协作者在你两轮之间所做的改动的唯一可靠办法。协作者会在轮次之间改同一个工作簿：每轮动手前重读活体文件
     并重新 diff，按刚读到的单元格干活而不是记忆里的版面（会插行、删格、文件被改名——先报，再用当前名）；
     文件可能在桌面表格软件里开着，就直接说，不要只写一个单元格的表面修复，对方下一次保存会覆盖你。
   - 只要作者以外的人会打开模型，就在文件里放一份阅读指南：表格底部一块紧凑说明（章节 | 哪些格是输入 |
     填什么 | 算法），每章一行重写的解释，每行一条注明该行用的基准（自有柜 vs 混装、实测 vs 估算）。
     把单元格地图只留在对话里，下一位读者一定再问一遍；每条长解释都要给足行高并自动换行——整行合并的解释行
     只有一行高，屏幕上被截成一行，打印时在页边被切断，即使表格本身看着没问题。
   - 可读性靠渲染验证，不靠想当然：无头转成 PDF，栅格化一页来看。被下一行盖住的文字，任何基于文本的检查
     都看不见，所以一次干净的逐格值 diff 完全可以通过一个没人看得懂的模型。
10. **把规则写成人和机器都能判定的形式。**
    - 两层共用一套编号和一套判据：人读的检查清单与机器规则页用同样的节点编号、名称和完成判据；机器页自创
      状态名，立刻变成两套说法。先把内容层写全，再做结构化。
    - 每个节点写九要素：编号 · 进入条件 · 何时提醒 · 必须齐什么 · 何时必须齐 · 检查什么 · 缺了找谁 ·
      完成证据/判据/下一节点 · 依据。不单列"何时必须齐"会误报：后面节点才产生的资料，在更早的节点只能写
      "提前提出要求"；完成判据不许写"齐了→过"，要写"检查通过；涉及人工门禁的，等确认人确认后再进入下一节点"
      ——检查通过不是放行。
    - 不要把不同记录组的数量写成一个等式：主合同数量、补充合同数量（带后缀）、执行调整是三组不同记录，
      写成"A = B = C"在有补充或调整的单上必然误报。改为分组核对，并注明汇总口径（这张汇总含不含补充合同、
      用的是哪个数量字段）。
    - 细节口径以现行规范为准，且改一处要同步多处：证照要哪几张照片、某个性能参数、型号怎么写，往往同时写在
      检查清单、资料表和角色手册里，只改被点名的那一处，下一轮审阅又会挑出"两处说法不一"。
    - 别人（另一个 AI、审阅人）指出的问题，常常在别处也有同款：成立的那条改完后，grep 全库找同款一起改，
      不成立的当场写明理由。多轮审阅意见按序号累加登记在同一件事的台账条目下，不新开条目、不另起文档。
    - 整篇覆盖式改写会静默丢内容：旧版段落无声消失，直到审阅才发现。改写前把旧版关键项 grep 成清单，
      改完读回逐项数命中次数——掉到 0 的就是丢了。
    - 发布状态要写清"已发布 / 待实施"。规则页写完不等于在运行：只要接口没接通、工作流被停用或权限没复验，
      就写"规则已就绪、运行待实施"，否则所有人（包括业务方）都会以为已经在自动执行。
11. **归档，并留一份旧标识映射。** 被取代的文档移进归档目录，不删：登记表的 `source` 列指着它们，删掉就断了
    审计链。按业务方要求删除任何东西之前，先提取并确认：只此一份的原始事实和控制数、字段 id 级的技术证据
    （重建时否则要重新找的 id 与公式字符串）、值得留的经验。登记表里留一份旧标识映射——旧表或工作表代码
    到现名，加上每份归档文档装过什么、被哪条条目吸收。归档日志、旧作业单和执行者配置仍在引用旧代码；
    按旧名配的工作流查的是一个已不存在的东西，表现为"表找不到"，而不是"规则过期"，所以没人会把它和改名联系起来。
12. **把算式露出来再报。** 报"两边对不上"时，把算式拆成步：先说是哪两个数、哪张表各汇总了什么，再逐行
    展开乘法（数量 × 单价 = 金额），再拿源单逐项相加——"这怎么算的、我没看明白"的意思是算式没露出来，
    不是数字错了。结论和决定性数字放最前，用平实文字，该用表格时用表格；按编号逐条回答，同一轮里把已授权的
    动作做掉；该主动提的冲突要提，因为"这个数和你自己的主数据矛盾"比一份干净摘要更值钱；最后只留一个需要
    拍板的问题，写成一句话能定。被问"这段是按基准 A 还是 B 算的"，就从文件里读出活公式，逐行并排展示，
    再点出真正用另一基准的那几处——困惑通常来自两个列在某一段里恰好同值（把按柜的数量填进了数量列），
    所以要解释它们为何看起来一样。复用上一批按柜费用的估算，必须连同假设一起交：费用与柜数成正比、单价不变、
    柜内同质，并说明哪些行符合假设（自装整柜的型号）、哪些被它歪曲（混装搭乘的型号），因为客户报价就是
    按这个数报的。选能长期自己运维的最简结构：为完整性提的额外字段或新表，被以"更复杂"为由否掉时，
    一句话接受、把否决登记下来，退到最轻的方案——能在关键路径上被违反的区分是一条写下来的纪律，
    不是一次表结构改动。

## 必查项

报出之前，逐条确认。示例只是示意，不限定检查范围。

- **过期数字还在屏上：** 改过引用数字的条目后，grep 登记表和每个活体件里的旧值，并重算每张派生表。
- **正文与附录条目集合相等**，`source` 指向登记表自身或只写版本号的行数为 0，`landed` 读自活体系统而非计划。
- **每处表结构改动都有证据：** 被取代的 id 变体都匹配到、`§N` 引用按从大到小重编号、正文与改前备份 diff。
- **每次插入式编辑都读回**，报工作簿改动前先逐格 diff：旧行完整、新条目独占一行，值和公式都比过。
- **逐载体数过被取代词**，剩下的每处命中都归为"取代说明"或"历史行"。
- **可读性靠渲染验过**，不是从一次干净的值 diff 推断出来的。
- **发布状态写明：** 已发布，或已就绪、运行待实施。

## 示例

只作示意，落地时换成你自己业务里的字段与值。

- 一条运费规则只活在聊天里，后来在费率表里被重述成相反的阈值。

## 坑

- 规则只活在日志或聊天里，下一份凭记忆写的文档就会和它冲突；写成建议的规则会被读成可选项。
- 前缀与实体名撞车，或编号与表代码只差一个字符，每个读者（包括 agent）都会误读；定位不到来源的决定无法复核。
- 严格的条目 id 正则静默跳过被取代的变体，恰好是没人检查的行渲染坏掉；重编号顺序错会层层串改已被移动的文字。
- 只替换行首片段的插入会把旧行尾巴粘到新条目上，两行并成一行。
- 各费用池混用分摊机制：都合计 100%，分出来的费用却不同，两份文档都解释不了这个差；标签与单元格含义不符，
  等于请人把错的数填进对的格。
- 靠重读来数被取代词会漏载体；定时巡检会一直跑下去，也照样漏。
- 删掉归档文档会断 `source` 链；缺了旧标识映射，以后表现为"表找不到"。
- 整篇重写会静默丢段落；发布状态不写清会被读成"已经在跑"；就地编辑只报"改好了"等于"什么都没发生"。
- 在桌面软件里开着改的工作簿，下次保存会覆盖你的改动；单元格地图只留在对话里、解释行不给行高，
  模型只有作者自己看得懂。

## 自检

- 规则以条目形式存在：有可定位的来源、有状态、有读自活体系统的 `landed`。
- 没有任何载体还带着过期措辞（取代说明和历史行除外）。
- 每个改动的值都有改前/改后，并有一次控制数校验。
- 没核实、没扫到、还没运行的部分，都照实写明。
