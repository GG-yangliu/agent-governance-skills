# 已部署的自动化不好使，怎么查

用户在无代码／agent 平台上已经搭好一个自动化，但它做的不是用户以为的事：「我配的自动化不管用」「部署了但不知道怎么用」「每次都感觉配得不对」「bot 回复的内容是错的」「流程根本没触发」「太重了」。故障可能在触发器、部署、输出或数据上。**先查出是哪一处，再动手改。**

要跑起来就能测的代码 bug 不归本技能管，那是普通的调试。

## 工作流

用户的说法和配置本身都不是证据。用户会报一个症状（「它不管用」），又另外断言一个状态（「那个我已经配好了」「它没接上」），而这些断言两个方向上都经常是错的。配置没法告诉你它到底**跑没跑过**，只有运行产物能。按下面顺序取证，第 3 步之后再形成假设。

1. **先读目的地的运行记录。** 只要自动化会往任何地方发东西，就直接读那个地方：每一条消息、从最早一条读起，带发送方、时间戳和完整正文。这一读同时回答「跑过没有」和「输出能不能用」，还能推翻用户自己的说法。自建立起消息的**条数**本身就是诊断结论：该被触发的频道里一片安静，就证明触发器从没触发。
2. **把触发器当成数据侧的一件活对象去找**：表的自动化列表、定时条目、webhook 注册记录。目的地里没有任何它触发过的痕迹，说明出问题的是触发器，不是动作。
3. **列出每一个候选版本的部署状态。** 用户反复改过的项目如果报「无部署历史」，意味着**他在修的东西不是实际在跑的东西**——这是「我改了、没效果」最常见的原因。读代码之前，先把所有版本的部署状态列出来。
4. **查搭建历史和当初的需求。** 搭建时的对话里有最初的诉求和每一次改动。从里面挖出「被要求过但从未实现」的部分。
5. **再查自动化读的那份数据。** 到这一步才问：那些字段真的是结构化的吗？见必查项里的基线卫生。
6. **把诊断写成文件**，放在用户自己的工作日志位置，用用户的语言，顺序如下：一句话说结论；你实际查到的事实，每条带它出自哪个产物；根因，按严重度编号；修正方案，最独立最便宜的先做；只有用户能拍板的几件事；附可复现命令和触碰过的每一个对象 id，让下一次接手不用重新摸索。
7. **在对话里**：结论先说，讲清证据推翻了你前面哪个猜测，把文件路径交出去，最后收在一个需要用户定的决定上。对着产物拿到确定的诊断**就是**交付物——用户还没选方向之前，不要滑到重做里去。

### 配好的东西突然不见了

用户说一个本来能用的集成突然没了：`<app>` 里的助手不见了、面板空了、插件不进菜单。**不要先去查配置是不是丢了，也不要猜是升级覆盖了。**

1. **先证明东西没丢。** 配置文件、命令行版本、历史记录、授权凭据逐个点名，并真跑一个最小请求，看返回什么。先把「我配的都没了」这个恐慌消掉，再谈缺陷。
2. **把「上次能用那一次」和「这一次」的启动日志并排对比。** 日志通常按启动时间分文件夹（每启动一次一份），在同一路径下对同一个功能名各 grep 一遍：能用的那份有组件激活、计数非零；坏的那份只有 `Count: 0` 或 `not downloaded yet`。**差异本身就是诊断**，比读代码快。
3. **区分「配置缺失」和「运行时组件没落地」。** 日志里出现 `not downloaded`、`Count: 0`，或者 provider 已注册但能力为零，都是运行时产物缺失，不是用户配错。去找它的缓存目录（一般在应用的用户数据目录下，带 `<组件>/<版本>/<平台三元组>` 层级），看有没有完成标记文件（如 `.complete`）；没有就是从没装成。
4. **手工补齐后，只重启承载它的那个子进程。** 把官方分发的产物解到缓存目录、补上完成标记，然后只结束那个子进程，让主程序自己把它拉起来。不要重启整个应用，打断用户手上的活。重启后再读一遍日志：计数应该回来了，历史条目也重新注册了。
5. **版本升级会让缓存键失效。** 产物缓存路径里含版本号，升级后旧产物不再命中。交付时写一句：下次大版本升级可能再来一次，叫我重放。

这一类的汇报顺序：先一句「你配的东西一个都没丢」加一条实测证据，再讲缺陷的机制——是哪一层传不出来，最后给一个用户一句话就能定的动作。不要用「可能是升级导致的」这类猜测收尾：没坐实的机制不如不说。

## 必查项

报诊断之前逐条过。示例只是示意，不限定你要查的范围。

- **拿「实际部署的东西」对「改过的意图」，不要对计划。** 同一个意图常常并存两个版本：一个体量大、正在线上被打补丁，一个轻量重写、从没部署。两个版本的部署状态都要报，并点名该退役哪一个；绝不去调那个没在跑的版本。
- **先确认平台的流程能不能自己拥有触发器。** 多数工作流／agent 产品是**拉模式**：只有被调用时才跑，没有原生触发器去盯数据库行变化或聊天消息。所以「表变了 → 工作流跑」这种设计整条缺了触发源——它必须来自数据侧的平台原生自动化、一个定时，或者由一个知道变化发生的地方显式发起 HTTP 调用。这是架构错误，查流程内部任何东西之前先查它。
- **API 返回空，不等于东西不存在。** 有些功能由不止一代 API 提供；列表接口返回零行，可能只是它看不见在界面上建出来的对象。不要据此下「你根本没配过」的结论。报原始返回，讲清不确定在哪，再给用户一个一眼就能核对的手工检查。
- **先修基线，再修比对。** 自动化拿新数据对一份存着的基线时，先查基线的字段卫生。没结构化的基线——整段话塞在一个文本字段里、结构化字段全空——会让每一步解析和比对永远失败，流程重写多少次都一样。反复出现的 JSON 解析报错是数据的症状，不是代码的症状。
- **编造的值指认没接上数据的那一步。** 源表里根本不存在的标识、规则要求引记录却被留空的小节、重复的段落、正文里裸的 JSON：每一种都说明那一步在「生成」而不是在「读」。每种都配一条硬约束（不许造 id、必须引真实源行 id、不许裸 JSON、去重、锁输出模板），不是重试，也不是把同一段提示词再部署一遍。
- **把需求漂移列成表。** 用户最新口述的需求经常和已写死的逻辑相反——「没变化就别说话」对上一个每次都发「本周没有新情况」。把新旧并排列出，让用户选；不要默默挑一个。
- **「太重」是诊断结论，不是情绪。** 一个这种体量的业务，却带着鉴权层、试运行开关、各种闸门开关的版本，就是过度设计。直接说，并给出更小的形态，而不是硬把大的那个弄通。

## 示例

只作示意，落地时换成你自己的平台、字段名和 id。

- 先看部署状态，再读代码：把所有候选版本列出来，逐个读它的部署状态——报「没有部署历史」的那个从没部署过，而状态成功、带可用入口的那一个才是外面真正打到的版本。所以从没部署的那个不是要调的对象。
- 本机定时器：`<agent-home>/scheduler/runs.db` 里这个任务一行都没有，最后成功标记停在 <日期> 没往前走——这只排除了这一台主机。
- 两次启动的日志对比：能用的是 `activate <组件>`、`<功能> refreshed Count: 42`；坏的是 `Count: 0`、`not downloaded yet`。
- 没接上数据的输出：一个在源表里找不到对应行的 id、一个空的引用小节、同一段话出现两次、正文里留着裸 JSON。
- 需求漂移：早先是「没变化就别发」，现在是每次运行都发「本周没有新情况」。

## 坑

- **假定触发器存在之前，先找到定时器在哪。** 用户记得的那个周期任务（「每周一 9 点跑」）可能不在你所在的这台主机上——它可能是某台 agent 主机自己的定时器、平台侧的流程触发器，也可能压根不存在。先查本机定时器，并把查到的东西当证据报出来：任务列表、本机定时与执行记录里的行数、以及最后成功标记有没有往前走。本机排程是空的，只排除掉一整种解释，不证明任务从没建过——要说清你查的是哪台主机，不要下结论。
- **没部署过 ≠ 没跑过。** 本机排程为空，**加上**某个候选项目报无部署历史，两者合起来只证明这两个都不是在跑这个任务的那个。同一个周期任务可能归平台自己的调度器、另一台 agent，或者那个平台上的另一个账号。措辞要写成「我查了主机 X 和项目 Y，两个都不拥有这个排程」，然后先问用户是谁在跑，再写「它没跑过」——这里错一个否定，整份报告里其他发现都跟着失信。到目的地去印证：任务本该写的那条记录（比如「最近核查时间」「最后更新」这种表字段）或频道里的那条消息才是真痕迹，时间戳才分得清「跑过」和「从没跑过」。
- **不要停在「链接断了」。** 东西在跑但输出是坏的，交付物是那份修输出的约束清单、由用户确认——不是重做。
- **表结构常常还有一份测试／草稿副本和正式副本同时在用**，自动化可能指着其中任一份。读记录之前先确认哪个对象是权威版本，并说清你的发现来自哪一份。
- **不要只读最近的运行消息。** 建好之后最早的那几条才带着最初的故障；最新的那条可能是人工跑的一次测试，把问题盖住了。
- **不要把用户自己过时的规格当成他现在的意图。** 旧设计文档里的老对象／字段编码会落后于线上表结构；先核映射，再下「自动化指错了对象」的结论。

## 自检

- 报告里每条发现都点得出出处——某个消息 id、某条记录、某个部署状态字段——不是从配置推的。
- 用户实际在跑的是哪个部署版本，由部署状态认定，不是假设。
- 核实不了的东西，在报告里标成未核实。
- 第 3 步的证据没点明哪个候选版本在跑之前，没有提出任何修正方案。
